# 数据字典：这个 Agent 到底记录了什么

> 本文说明每张表、每个字段能回答什么问题。
> 一句话：**每次请求落一行记录，13 个字段，其中 `baseline_cost_cny` 是整个方案能说"省了多少"的根基。**

---

## 一、落盘位置

| 文件 | 内容 | 生成方式 |
|---|---|---|
| `runs.db` | SQLite 单表 `runs`，每次请求一行 | 服务运行时自动写入（`app/store.py`） |
| `eval/result_stdlib.csv` | 评测逐条明细，多两列人工标注 | `python eval/run_eval_stdlib.py` |
| `docs/evidence/bench.csv` | 并发压测结果 | `python tools/bench_stdlib.py` |

---

## 二、`runs` 表 13 个字段

### A. 请求标识（3 个）

| 字段 | 类型 | 含义 | 有什么用 |
|---|---|---|---|
| `id` | INTEGER | 自增主键 | 请求序号，便于回查 |
| `ts` | TEXT | 时间戳，精确到秒 | 按小时/天聚合，画流量与成本曲线 |
| `query` | TEXT | 原始请求，**截断 500 字** | 事后抽检"哪些请求被分错了"；截断是为了防长文撑爆数据库 |

### B. 路由决策（3 个）—— 最能体现工作量的部分

| 字段 | 类型 | 取值 | 有什么用 |
|---|---|---|---|
| `route` | TEXT | `easy` / `hard` | 最终路由结果 |
| `reason` | TEXT | 如 `命中强特征:写一个`、`短句无强特征`、`兜底:长`、`强制easy`、`命中强特征:写一个(本地不可用)` | **可解释性**：每个决策都能说清为什么，不是黑盒 |
| `decided_by` | TEXT | `rule` / `model` / `default` | **哪一层做的决定**。统计三层各占多少，就是规则层覆盖率的直接证据（消融实验靠它） |

> `decided_by` 是这张表里最容易被忽略、但复盘时最有用的字段：它把"规则层拦掉了多少请求"从一句话变成了一行 SQL。

### C. 执行结果（3 个）

| 字段 | 类型 | 含义 | 有什么用 |
|---|---|---|---|
| `model` | TEXT | 实际调用的模型；升级时为 `Qwen2.5-7B-AWQ -> deepseek-chat` | 证明"这一条真的走了哪条路" |
| `latency_ms` | INTEGER | 端到端延迟，**含路由自身耗时** | 三策略延迟对比；不藏路由开销 |
| `escalated` | INTEGER | 0/1，是否触发质量自检升级 | 升级率 = 自检机制的触发频率，用于评估阈值是否合理 |

### D. 成本记账（4 个）—— 核心

| 字段 | 类型 | 含义 |
|---|---|---|
| `tokens_in` | INTEGER | 输入 token 总量，**含路由分类消耗的那 20–30 token** |
| `tokens_out` | INTEGER | 输出 token 总量，**含升级重答的那一份** |
| `cost_cny` | REAL | 本次真实成本。本地按内部折算单价（默认 ¥0.0028/1k），云端按 API 牌价（入 ¥0.005 / 出 ¥0.015 per 1k） |
| `baseline_cost_cny` | REAL | **反事实基线**：同样的 token 量**全部走云端**会花多少 |

**为什么 `baseline_cost_cny` 是关键设计**

如果只记 `cost_cny`，你只能说"这次花了 0.000053 元"，说不出省了多少。有了基线，节省比例就是逐条算出来再求和：

```
节省比例 = 1 - Σ cost_cny / Σ baseline_cost_cny
```

这是**实测累加**，不是拿平均数估算的。"混合策略比全云端省 X%"里的 X 就从这里来。

**升级的代价没有被藏起来**

质量自检触发升级时，本地那次的 token 和云端重答的 token **累加进同一行**。所以"升级"不是免费的兜底，它的成本会如实出现在 `cost_cny` 里——这正是评估"自检阈值定得值不值"的依据。

## 三、派生指标（不存表，查询时现算）

`app/store.py` 的 `stats()` 一条 SQL 出 8 个数：

| 指标 | 计算 | 用途 |
|---|---|---|
| `runs` | `COUNT(*)` | 样本量 |
| `cost_cny` | `SUM(cost_cny)` | 实际总成本 |
| `baseline_cost_cny` | `SUM(baseline_cost_cny)` | 反事实总成本 |
| `saved_ratio` | `1 - cost/base` | **核心结论数字** |
| `avg_latency_ms` | `AVG(latency_ms)` | 体验指标 |
| `escalated` | `SUM(escalated)` | 升级次数 |
| `easy` / `hard` | `GROUP BY route` | 路由分布 |

`/api/stats` 接口和演示页顶部的统计条都来自这里。

## 四、评测另存的 `result_stdlib.csv`（13 列）

比 `runs` 表多两列，因为它要算**准确率**：

| 多出来的列 | 含义 |
|---|---|
| `gold` | 人工标注的正确难度（ground truth） |
| `error` | 失败原因（超时/连接失败/空答案），空表示成功 |

有了 `gold` 和 `pred`（即 `route`）才能算路由准确率；有了 `error` 才能说清"失败 3 条"是哪三条、为什么失败。

## 五、明确**没有**记录的（已知局限）

| 缺什么 | 影响 | 如果补要怎么做 |
|---|---|---|
| **答案正文** | 无法事后做质量人工复核，只能当场看 | 加一列 `answer`，脱敏后存 |
| **TTFT（首字延迟）** | 只有总延迟，分不清是排队还是生成慢 | 流式接口里打点 |
| **模型版本号 / 权重哈希** | 换模型后数据不可比 | 加 `model_version` |
| **user_id / session_id** | 做不了多轮对话分析、分不出单用户成本 | 加两列，注意隐私 |
| **失败类型细分** | 只有 `error` 文本，没分类 | 加 `error_type` 枚举 |

> 把已知局限写清楚，比藏着好：它说明你知道一个生产级记账系统还该有什么，只是 P0 阶段按性价比砍掉了。**"我知道缺什么"本身就是工程判断的证据。**

---

## 六、一句话总结

> 本系统对每次请求记录 13 个字段，覆盖**请求标识、路由决策、执行结果、token 级成本**四类。其中路由决策记录到"由哪一层、因何原因判定"，使决策可追溯；成本记录同时保存实际开销与"全走云端"的反事实基线，使节省比例可逐条累加求得而非估算。所有数据落在单文件 SQLite 中，零依赖、可随仓库分发、可直接用 SQL 复查。
