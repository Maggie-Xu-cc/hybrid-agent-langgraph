# Hybrid Routing Agent

一个**成本感知的混合推理 Agent**：本地小模型处理简单请求，复杂请求自动升级到云端大模型，并把每次调用的 Token、延迟、成本都记下来。

> 主流程用 LangGraph `StateGraph` 编排，带会话记忆、语义缓存、RAG 检索与可切换的双链路（图编排 / 显式流程）对照评测。
> 核心不是"又一个聊天机器人"，而是回答一个问题：**在什么条件下，自建小模型 + 云端兜底比全部走 API 更划算？**
>
> 成本与质量两条线同时管：**语义缓存命中（0 成本）→ 检索资料（0 成本，决定答得准不准）→ 规则层拦下大部分请求（0 成本）→ 本地小模型承接简单请求（低）→ 云端大模型只处理真正难的（高）**。

## 在线试用

**https://hybrid-router-agent.app.workbuddy.host/?sharecode=CLU3I2I6TH**

一句话说明它和本地的差别：**云端容器没有 GPU，所以线上是纯云端形态**——路由、缓存、记忆、记账的逻辑与本地完全一致，只是"简单请求"那一层由云端代答。页面上会明确标注当前是哪一层产出的答案，不会把云端的结果说成本地小模型的功劳。

额度 300 次/天、单 IP 10 次/分钟：这是个人项目，背后是真实 API 计费，限额是为了让最坏情况的支出可预期。

想看完整的混合链路（真·本地小模型承接），按下面「本地运行」起本地模型即可。

## 架构

```
                 ┌──────────────────────────────┐
   HTTP 请求 ──▶ │  FastAPI  (app/server.py)    │
                 └──────────────┬───────────────┘
                                ▼
                 ┌──────────────────────────────┐
                 │  路由 router.py              │
                 │  规则层 → 模型层 → 兜底层    │
                 └───────┬──────────────┬───────┘
                    easy │              │ hard
                         ▼              ▼
              ┌────────────────┐  ┌────────────────┐
              │ 本地 Qwen2.5-1.5B│  │ 云端大模型 API │
              │ transformers/ROCm│  │ OpenAI 兼容    │
              └───────┬────────┘  └───────┬────────┘
                      │  自检不通过 → 升级 │
                      └──────────┬────────┘
                                 ▼
                    ┌────────────────────────┐
                    │ 记账 store.py (SQLite) │
                    │ token / 延迟 / 成本     │
                    └────────────────────────┘
```

**设计要点**：本地推理服务与云端 API 都走 OpenAI 兼容协议，所以"路由"退化成一次 `base_url` 切换，不需要维护两套调用逻辑。平台镜像未提供 vLLM，本地服务由 transformers + 标准库 HTTP 自建（`deploy/local_server.py`，120 行），上层零改动。

## LangGraph 编排（v1.1）

主流程迁移到 LangGraph `StateGraph`（`app/graph.py`），行为与原显式流程（`app/agent.py`，保留为基线）完全一致：

```
START ─▶ load_memory ─▶ cache_lookup ─命中─▶ bookkeep ─▶ save_memory ─▶ END
                             │
                             └未命中─▶ retrieve ─▶ route ──easy──▶ local_answer ─▶ self_check ─需升级─▶ escalate ─┐
                                                      │                                │                         │
                                                      └──hard──▶ cloud_answer          └─通过─▶ bookkeep ◀───────┘
                                                                 (cloud_answer ─────────────────▶ bookkeep)
```

- 路由逻辑 `router.decide()` 原样保留，从"函数调用"变成**条件边**；记账集中在 `bookkeep` 节点
- **会话记忆（短期）**：`SqliteSaver` checkpointer 按 `session_id` 持久化对话状态（`checkpoints.db`），天然支持多轮对话
- **双链路可切换**：`ENABLE_LANGGRAPH=1/0`，两条链路跑同一份评测集可做对比实验
- 冒烟测试（离线）：`python tools/smoke_langgraph.py`

### 上下文工程（v1.2）

`app/context.py` 按 token 预算组装 prompt，而不是简单截断：

```
system 人设（必留）＋ 长期记忆事实（≤200 tok）＋ 早前摘要（≤300 tok）＋ 最近对话（≤800 tok）＋ 本轮问题（必留）
```

- token 估算用字数折算（中文 0.75/字、其它 0.3/字符），不为估算引入 tokenizer 依赖
- 记忆块装不下时**整块丢弃**，不塞半截；每轮的注入统计（各部分 token、裁剪条数）随响应返回（`memory.ctx_tokens`），上下文是可观测的

### 长期记忆（v1.2）

`app/memory.py` 跨会话记住用户的关键事实，`session_id`（短期）与 `user_id`（长期）两个键独立：**新会话不会忘掉用户，新身份读不到别人的会话**。

- 抽取用正则（`我叫X / 我在做X / 我最喜欢的X是Y / 记住：X`），带疑问句过滤（"我在做什么项目？"不会把"什么项目"记成事实）；每轮的判断成本是 0
- 存储 SQLite 单表 `(user_id, fact_key, fact_value)`，覆盖旧值即记忆更新；事实量级小，全量召回就是最优检索，暂不需要向量库
- **历史摘要压缩**：对话超过 20 条时，把最老的部分用本地小模型压成摘要（失败退化为逐条截取），保留最近 12 条——历史的上限从"硬丢弃"变成"软压缩"，摘要调用的 token 照样记账

前端身份存 `localStorage`（默认生成，可与 `session_id` 分别重置）；「忘掉我」按钮清空当前身份的长期记忆，历史会话不受影响。

- `GET /api/memory/{user_id}` → 查看已记住的事实
- `DELETE /api/memory/{user_id}` → 清空某身份的长期记忆
- 冒烟测试（离线，26 项断言）：`python tools/smoke_memory.py`

### 语义缓存（v1.3）

`app/cache.py` 插在路由**之前**：相似的问题直接复用上次的答案，成本降为 0。降本链路完整变成四级：

```
语义缓存命中(¥0) ─▶ 规则路由(¥0) ─▶ 本地小模型(低) ─▶ 云端大模型(高)
```

实现要点（每条都是面试可展开的取舍）：

- **两级过滤，缺一不可**：向量粗筛判「讲的是不是同一件事」，载荷守卫再判「参数是否一致」（数字 / 单位 / 缩写 / 说法 / 褒贬）。只用向量时 precision 66%，加上守卫到 100%——**因为句向量天生看不见 3点15→3点45 这种一字之差**，详见下面的校准记录
- **向量用本地小模型，仍然零 API 成本**：BGE-small-zh-v1.5（ONNX + CPU，512 维，单条约 4ms）。"缓存不能自己花钱"这个直觉是对的，但零的是 API 成本、不是零模型。模型缺失时自动退回 n-gram 后端（`EMBED_BACKEND=auto`），主流程不受影响
- **阈值随后端自动取**：bge→0.60、ngram→0.35（`CACHE_THRESHOLD=0` 表示自动）。两个后端的分数分布完全不同，阈值不能互相搬——换后端必须重新标定
- **只缓存首轮独立问题**：多轮问题（"继续""为什么"）依赖会话上下文，换会话直接复用会答错——宁可少命中，不可答错。hard 请求默认不缓存（质量敏感+重复率低），`CACHE_CACHE_HARD=1` 可打开
- **两段式查找**：归一化 hash 精确匹配 O(1) 优先，再相似度线性扫描（条目量级小，毫秒级）；等量级上万再上向量库
- **TTL 过期**（默认 7 天）+ 命中刷新：过期答案可能已过时（"今天天气"），一律不返回
- **三条失效路径**：TTL 管"时间让答案过时"、`embed_model` 管"换了向量后端维度不同不能比"、`kb_version` 管"知识库改过、基于旧文档的答案不成立"。第三条原来是"检索命中就不写缓存"，导致线上有知识库时缓存条目恒为 0（详见 `docs/code-reading.md` 第 17 节）

#### 阈值校准记录（v1.6：0.45 被推翻）

早期版本用 n-gram + 阈值 0.45，验证方式是「24 个问题跑三遍看命中率」。这套验证有个致命缺陷：
**测试集里只有"该命中"的样本，没有"不该命中"的**，所以任何阈值都显得很好。

补齐 26 条「正确答案不在缓存里」的危险样本后（`eval/pairs.jsonl`，89 条），
扫遍 0.20~0.99 得到的结论是：**那个阈值不是调得不准，是尺子不对**。

| 配置 | 最优阈值 | 命中率 | Precision | F0.5 | 错误率 |
|---|---|---|---|---|---|
| n-gram | 0.35 | 59.6% | 56.6% | 0.579 | 25.8% |
| n-gram + 守卫 | 0.35 | 33.7% | 96.7% | 0.868 | 1.1% |
| BGE | 0.60 | 69.7% | 66.1% | 0.693 | 23.6% |
| **BGE + 守卫** | **0.60** | **47.2%** | **100.0%** | **0.972** | **0.0%** |

关键一点：命中率从 59.6% 掉到 47.2%，但**错误率从 25.8% 归零**。这个交换是值得的——
漏命中只是多花一份钱，误命中是让用户拿着错答案去办事。
完整曲线、AUC、被守卫拦下的案例见 `docs/evidence/threshold_sweep.md`，
一键复现：`python tools/threshold_sweep.py --write`。

评测时显式关缓存（`run_graph(..., use_cache=False)`），否则同义用例第二次出现命中缓存，污染对照实验。

- `GET /api/cache` → 缓存概况（条目/命中/省下的 token 与成本）
- `DELETE /api/cache` → 清空缓存
- 冒烟测试（离线，46 项断言）：`python tools/smoke_cache.py`
- 阈值扫描（四种配置对照，输出 P/R/F0.5 曲线）：`python tools/threshold_sweep.py --write`
- 下载本地向量模型（91MB，可选）：`python tools/fetch_model.py`
- 基准（两遍原始问题 + 一遍改写问法）：`python tools/cache_bench.py`（加 `--mock` 离线跑）

### RAG 检索（v1.6）

`app/rag.py` 补上「上下文工程」缺的那一环：前面几版解决的是"预算怎么分"，但没有**检索**——
模型不知道你的文档里写了什么，问"这个项目的缓存阈值怎么定的"只能编。现在链路完整了：

```
语义缓存(¥0) ─▶ 检索(¥0) ─▶ 规则路由(¥0) ─▶ 本地小模型 ─▶ 云端大模型
                  │
                  └ 命中则把片段注入 prompt 的「参考资料」块（上限 500 token）
```

四步流程，每步的取舍都能单独讲：

1. **切块**：按 markdown 标题分节（作者自己划的语义边界，比定长滑窗准），节内按段落聚合到 450 字。太短的块（<80 字）不入库——全是噪声
2. **召回**：BM25（中文按字符 bigram，去停用词）+ 向量余弦两路
3. **排序**：BM25 归一化 85% + 向量 15%
4. **过滤**：BM25 绝对门槛 + 命中词项数 ≥2 + 命中至少一个关键项 + 相对分数截断

**这里有一段实测驱动的设计修正，比功能本身更值得说：**

初版用的是工业界默认的 RRF 融合（两路排名倒数相加）。跑出来是错的——问"缓存阈值是怎么定下来的"，BM25 正确地把 `§13.3` 排第一（13.79 分），但融合后第一名变成了一块 BM25=0 的无关块。根因：RRF 假设两路都有判别力，而 **n-gram 向量在"短查询 vs 长文档块"场景下没有判别力**——查询只有 8 个 bigram，文档块有几百个，归一化后点积被长块的主导维度稀释，分数全挤在 0.25~0.5 的窄带里（实测相关 0.30~0.51、无关 0.27~0.40，完全重叠）。所以改成显式加权，向量只保留 tiebreaker 的角色。

第二个坑：**IDF 最高的词不一定是"重要"，可能是"从没出现过的垃圾"**。问"SQLiteSaver 为什么会报 readonly"，中文部分切出"么会""会报"两个跨词边界碎片，它们在语料里一次都没出现，IDF 冲到最高被当成关键项，而真正该命中的 `readonly` 反而被排除 —— 这条查询直接漏召。改成按 **DF**（出现次数）判断且排除 DF=0：DF=0 不是"区分度高"，是"不存在"。

两个坑的共同点：**都是"以为标准做法能用"导致的，靠实测才发现**。

实测效果（148 块知识库，16 条查询）：

| 指标 | 结果 |
|---|---|
| 相关查询召回 | 9/9 |
| 无关查询拒绝 | 4/7（"今天天气"这类误召回，文档里恰好有该短语，靠提示词「不相关就忽略」兜底） |
| 检索耗时 | 30~35 ms（148 块线性扫描） |
| 命中时注入 | 2~4 段，约 300~500 token |

为什么不接 sqlite-vec / Chroma：和缓存同一个判断——几百到几千块的线性扫描是毫秒级，不值得引依赖；`embed()` 是独立函数，换真 embedding 模型只改它一处。边界也清楚：**向量路现在的贡献接近零，换成真 embedding 后才会明显，那时再调融合权重**。

- `python tools/build_kb.py` → 建/更新索引（改完 docs 要重跑）
- `GET /api/kb` → 知识库概况；`POST /api/kb/rebuild` → 重建
- 冒烟测试（离线，44 项断言）：`python tools/smoke_rag.py`
- 有检索结果时**不写语义缓存**——答案依赖知识库内容，改了文档缓存就过期

### 工具调用与 ReAct 循环（v2.0）

前面每一层解决的都是"答得省、答得对"，但都建立在一个前提上：**资料已经在手里**。
问"记账表里有多少条走了缓存"、"89 条里命中 47 条是多少"，再好的检索也没用——得真去查、真去算。
这一层让模型能动手：

| 工具 | 级别 | 干什么 | 防什么 |
|---|---|---|---|
| `search_docs` | 只读 | 检索本地知识库，按需取片段 | —— |
| `sql_query` | 只读 | 对记账库执行 SELECT | 写语句、多语句、缺 LIMIT、库为只读（`mode=ro`） |
| `fetch_url` | 只读 | 抓网页并转纯文本 | 域名白名单、内网地址（SSRF）、内容标记为"不可信资料" |
| `run_python` | **危险** | 临时目录跑一段 Python | 黑名单 + 超时 + 独立进程（**这不是真沙箱**，见文档） |

链路：`cache → route`（判"要不要动手"）→ `tool_agent`（想→调→看→再想）→ `bookkeep`。
动过手的答案**不写语义缓存**：它的正确性依赖"当时那一次"外部状态（表里几行、网页写了什么），
这些变化没有版本号可比，`kb_version` 管不了。

实测（本机，真实模型）：一条"统计记账表"2 步、2.1 秒、**¥0.014**——比普通问答贵约 3 倍。
这是"会动手"的真实价格，不藏。省的办法也有：工具路径会跳过预先 RAG（少注入约 1000 token），
因为它自己会调 `search_docs`，同一批文档没必要进两次上下文。

循环里真正要写的不是"调用模型"，而是四个兜底（都在 `app/react.py`）：

- **什么时候停**：步数上限 + "连续重复同一调用"提前收口。模型卡住时再多给 3 步只是烧钱。
- **模型胡闹**：参数 JSON 坏了、工具名写错、漏必填——**把错误当观察结果还给它**，它通常能自己改对。
  抛异常终止是最差选择：用户看到一个红叉，而模型本来能自救。
- **观察太长**：超 1600 字留头留尾并标注砍了多少。200KB 网页直接塞回 prompt 等于把上下文吃光。
- **钱**：单次 ¥0.05 预算，超了强制收口，并让它说清"还缺什么"。

安全上有一条不能省：**工具返回的内容是资料，不是指令**。网页里写"忽略之前所有指令"，模型也不许照做。
所以 `fetch_url` 的结果外面套一层"不可信"标记，系统提示里再写一遍规则。
真要执行危险动作，只能靠人工确认——那是下一步（HITL）要接的。

页面上每一次调用都会列出来：第几步、调了什么、参数是什么、结果几行、花了多久。
"调了 3 次工具"这句话本身没有信息量，能证明它会动手的是**每一步的参数和结果**。

### 历史会话可以切回去

页面是「左侧会话栏 + 右侧对话流」的布局（v1.8 改版）：左边只列**当前浏览器自己开过的对话**，点一条即切回该会话并回显消息，可以接着聊；右边是对话流，答案跟在提问下面，不用往下翻。

- `GET /api/sessions?limit=20` → 会话列表（全站）
- `GET /api/sessions/{session_id}` → 该会话的消息记录 + 每一轮的决策元信息（`messages` + `turns`）
- `GET /api/stats?session_id=xxx` → 统计（`summary` 全站累计，`recent` 只给该会话）
- `DELETE /api/sessions/{session_id}` → 删除单个会话（会话行右侧的 `×`，点两次确认）
- `DELETE /api/sessions` → 清空全部会话（左下「清空对话」，点两次确认）

前端只显示 `localStorage` 里记过的会话 id，所以**不会看到其他访客的提问**；`?s=<会话id>` 可直达某个会话（面试时提前把对照问题摆好，点开就是现场）。

实现上没有另建索引表：直接读 checkpointer 自己的 `checkpoints` 表拿线程列表，再用 `get_state(thread_id)` 取历史。排序用表内 `rowid`，时间从 `checkpoint_id`（UUIDv6，前 60 bit 是时间戳）解出来。这样**会话的唯一真相就是 checkpointer**，不会出现"索引表和实际记忆不同步"的问题。评测/冒烟脚本的线程（`eval-*`/`smoke-*`/`other-*`）会被过滤掉，不进用户界面。

删除会话走 checkpointer 的 `delete_thread()`（会同时清 `checkpoints` 和 `writes` 两张表），版本不兼容时回退为直接删表，保证不会留下"半截会话"。删掉当前会话后前端会自动开一个新会话，不会停在空壳上。

### 页面上怎么看见「门卫拦截」

缓存命中会显示紫色「语义缓存命中」+ 相似度；**没命中但被载荷守卫拦下**的，显示红色「门卫拦截」徽章和一块红色说明：

```
门卫拦截 · 这一轮拒绝复用缓存
有一条缓存候选，相似度 0.906 比 0.35 的复用线还高，
但守卫发现 数字不同：['24','3','45'] vs ['15','24','3'] ——
这一问的答案会不一样，复用就是给你别人的答案。已改走模型重新作答。
```

要做到这一步，后端得把"为什么没命中"也带出来（`lookup()` 只返回 `None` 的话，"被拦下"和"压根没有相似条目"在外部看起来一模一样，而这两件事的含义完全相反）：

- `cache.lookup_ex()` 返回 `{hit, score, blocked, blocked_text}`，`lookup()` 是它的薄封装
- 图里新增 `cache_blocked / cache_blocked_text / cache_top_score` 三个 state 字段，进 `result.cache_guard`
- 记账表 `runs` 增加 `session_id / guard_blocked / cache_score` 三列（老库自动 `ALTER TABLE` 补列），所以**历史消息也能重放出同样的徽章**，不是只有当场那一轮才看得见

> 实现细节：拦截必须在"过相似度线"之后才判定。早期版本先跑守卫再比阈值，结果相似度只有 0.12 的无关问题也被报成"门卫拦截"——把"压根不像"包装成"刚挡住一次事故"，属于编故事。`tools/smoke_cache.py` 第 9 组断言专门守这条边界。


### 重构前后一致性怎么验

评测脚本支持按链路跑，并在 `--engine both` 时逐条比对两条链路的结果：

```bash
python eval/run_eval.py                  # 基线 agent.py，产物 eval/result.csv
python eval/run_eval.py --engine graph   # LangGraph 链路，产物 eval/result_graph.csv
python eval/run_eval.py --engine both    # 跑两遍 + 逐条一致性对比
```

一致性对比输出示例（MOCK_MODE 下 24 条）：

```
| 对比项 | 一致条数 | 占比 |
| 路由判定 | 24/24 | 100.0% |
| 是否升级 | 24/24 | 100.0% |
| 答案文本 | 24/24 | 100.0% |
```

> 逐条一致 = 图重构是**行为等价的改写**，不是借重构偷偷调策略。这是重构最基本的验收标准。

评测时每条用例用独立 `thread_id`（`eval-<uuid>`），避免上一条用例的历史污染下一条，保证成本与答案可比。

## 本机怎么跑最快

没有 GPU、只有一台普通笔记本时，跑一轮完整缓存基准有三个提速开关，**可以叠加**：

| 开关 | 作用 | 省多少 |
|---|---|---|
| `DISABLE_LOCAL=1` | 完全不调本地，所有请求直接走云端 | 省掉每条请求白等本地的 2~15 秒 |
| `--easy-only` | 只跑 easy 用例（hard 按设计不进缓存，跑了也不计入命中率） | 调用量 72 → 39 次 |
| `--workers 4~8` | 并发发起请求（瓶颈是网络等待，不是 CPU） | 串行 19.8s → 并发 7.2s |

最快的一条命令：

```bash
DISABLE_LOCAL=1 python tools/cache_bench.py --easy-only --workers 4
```

本机实测（DeepSeek 云端，16 核 CPU，无本地 GPU）：

| 跑法 | 调用次数 | 耗时 |
|---|---|---|
| 串行 + easy-only | 39 | 19.8 s |
| 并发 4 + easy-only | 39 | **7.2 s** |
| 并发 4 + 全量（含 hard） | 72 | 25.6 s |

### 两个必须知道的坑（都已修掉）

**1. 超时默认 600 秒。** openai SDK 不给 `timeout` 时默认十分钟，本地模型"端口通但不回"
（Ollama 半死、vLLM 还在加载权重）会让每条请求白等十分钟，看起来就像卡死。
现在 `LOCAL_TIMEOUT` 默认 15 秒，且失败 2 次后**熔断**——冷却 60 秒内直接跳过本地，
调用立刻返回（实测 2146 ms → 0.00 ms），由上层走降级。冷却结束放一次试探，成功即恢复。

**2. 并发写 SQLite 会偶发 `readonly database`。** 根因是 WAL 的自动 checkpoint 需要独占访问，
多连接写同一个库时它永远抢不到，WAL 只涨不缩（实测涨到 4MB 上限）后**所有写入失败
且不可自愈**。修法是反直觉的：**改回单连接 + 全局锁**，建库只做一次，DB 层再加一层重试
（只重试 SQL，不重跑模型）。压测结果：60 次并发请求 **0 失败**，`ck.db-wal` 稳定在 4MB
不再膨胀。落盘串行化的代价是毫秒级，而瓶颈在网络调用上，吞吐不受影响。

> ⚠️ `DISABLE_LOCAL=1` 会跳过路由的模型层（第二层小模型分类），
> 路由只能靠规则层和兜底层，**准确率会下降**——实测有 6 条标注 hard 的被规则层判成 easy。
> 所以：**要快速看效果就用它；要写进报告的数字，请在本地模型可用时跑。**

### 语义缓存实测（v1.3）

> 2026-10-27，DeepSeek 云端真实调用，`DISABLE_LOCAL=1`（本机无 GPU），
> 13 条 easy 用例 × 3 遍，`python tools/cache_bench.py --easy-only --workers 4`

| 轮次 | 请求数 | 命中 | 命中率 | 总成本 | 平均延迟 | 相对基线 |
|---|---|---|---|---|---|---|
| 第 1 遍（缓存空，基线） | 13 | 0 | 0% | ¥0.0090 | 1051 ms | 100% |
| 第 2 遍（相同问题，精确命中） | 13 | 13 | **100%** | ¥0.0000 | **0 ms** | **0%** |
| 第 3 遍（改写问法，语义命中） | 13 | 9 | **69.2%** | ¥0.0055 | 391 ms | 61% |

三点如实说：

- **第 2 遍成本归零**：完全相同的问法走 md5 精确通道，命中即返回，0 token 0 元 0 ms。
- **第 3 遍 69.2% 是 n-gram 方案的真实天花板**：它只认字面 n-gram 重叠，换个说法问到
  "结构不同但意思一样"时就漏。这组数据是**改造前**的对照基线（v1.3，n-gram + 阈值 0.45），
  v1.6 换成 BGE 向量 + 载荷守卫后，同一批评测集上语义召回 87.5%、precision 100%，
  见上文「阈值校准记录」。注意这套 bench 只测命中率、不测正确率——所以它给的 69.2%
  其实是虚高的，真实精度当时只有 56%。
- 全量（24 条含 hard）跑出来第 2 遍命中 19/24 而不是 13/24，多出来的是标注 hard 却被
  规则层判成 easy 的用例——因为 `DISABLE_LOCAL=1` 关掉了路由的模型层。
  要出报告数字，本地模型必须在位。

### 线上实测（2026-10-27 晚，公开链接上的四次真实调用，线上跑真 BGE）

线上已经带上 91 MB 的 BGE 模型（ONNX + CPU，2 线程），阈值自动切到 0.60。
`GET /api/cache` 可以自证：`{"embedder":"bge-small-zh-v1.5","threshold":0.6}`。

| 请求 | 页面显示 | 延迟 | 成本 |
|---|---|---|---|
| A「载荷守卫是怎么判断两个问题的参数不一样的？」 | 云端大模型 + **门卫拦截**（缓存里那条差一个数字） | 1046 ms | ¥0.0042 |
| B「门卫是怎么判断两条问题的参数不一样？」（同义改写） | **语义缓存命中**（相似度 0.809） | **0 ms** | **¥0** |
| C「载荷守卫…参数不一样的？**阈值 0.8 够吗**」 | 云端大模型 + **门卫拦截**「数字不同（问题里多 0/8）」 | 1901 ms | ¥0.0061 |
| D「明天上海会下雨吗？」（无关） | 云端大模型，**无拦截** | 714 ms | ¥0.0039 |

- **B 说明该复用的复用了**：换成 BGE 之后，"门卫"↔"载荷守卫"这种**换个词说同一件事**才
  真被认出来（相似度 0.809）。用 n-gram 时这类改写只有 0.1~0.4，根本过不了线——
  这就是换尺子换来的命中率（召回 61.7% → 87.5%）。
- **C 说明尺子看不见的那部分由守卫兜住**：0.8 和原文只差几个字符，向量觉得"非常像"，
  是字符串规则发现数字对不上才拒绝复用。**句向量天生看不见参数**（near-miss 上 AUC 0.394），
  这不是模型不够大，是任务不对口。
- **D 说明没有滥报拦截**：压根不像的时候不许显示"门卫拦截"——把"没命中"包装成
  "刚挡住一次事故"等于编故事。这条边界由 `smoke_cache.py` 第 9 组断言守着。
- 四次累计：成本 ¥0.0143，全云端基线 ¥0.0186，**节省 22.8%**（只有 1 次真命中，
  演示重点是"错的那次没被复用"）。

线上从此和本地同一套尺子：`prepare_bundle.py --with-bge` 会把 5 个模型文件塞进部署包
（292 KB → 91 MB），并往包里的 `requirements.txt` 追加 `onnxruntime`/`tokenizers`。
实测代价：内存 +97 MB、冷启动 +0.35 秒、每条向量 3~4 ms。**这 91 MB 值得带**——
不带的话线上和本地跑出来的命中率不是一回事，演示数字和证据对不上。

